# FixLedger 需求说明

## 1. 项目背景

FixLedger 是一个面向家庭场景的设备保修、维修、耗材更换和凭证归档工具。

日常生活中，家庭设备越来越多，例如手机、电脑、耳机、路由器、净水器、空气净化器、洗衣机、冰箱、扫地机器人等。这些设备通常来自不同购买渠道，发票、保修卡、说明书、售后截图、维修记录也分散在电商平台、聊天记录、相册和本地文件中。

当设备出现故障、需要维修或需要更换耗材时，用户经常会遇到：

- 不知道设备是否还在保修期。
- 找不到发票、保修卡和说明书。
- 忘记上次维修、更换滤芯或更换电池的时间。
- 维修费用和维修历史没有统一记录。
- 家庭成员之间设备信息不共享。
- 各品牌 App 只管理自家设备，缺少统一家庭设备档案。

FixLedger 要解决的是这个生活中的小问题：把家庭设备从购买、使用、保修、耗材更换、维修到报废的生命周期统一管理起来。

## 2. 项目定位

FixLedger 不是企业固定资产系统，也不是泛用后台管理系统，而是一个更贴近个人和家庭使用的生活工具。

核心定位：

- 管理家庭设备档案。
- 归档发票、保修卡、说明书、维修单等附件。
- 追踪设备保修期。
- 管理耗材更换周期。
- 记录维修过程和维修费用。
- 通过提醒减少遗忘。
- 使用 AI 辅助录入和总结，但不依赖 AI 完成核心业务。

## 3. 目标用户

### 3.1 家庭用户

家庭中负责购买、维护和管理家电、数码设备的人。

主要诉求：

- 统一查看家中设备。
- 快速找到发票、说明书和保修卡。
- 接收保修到期和耗材更换提醒。
- 记录维修历史。

### 3.2 家庭成员

家庭空间中的其他成员，例如配偶、父母、室友。

主要诉求：

- 查看设备信息。
- 补充维修记录。
- 查看耗材是否需要更换。
- 查看售后联系方式和凭证。

### 3.3 租房用户

管理租住房屋内自购设备或房东提供的设备。

主要诉求：

- 记录设备归属。
- 记录维修费用。
- 保留维修证据。

### 3.4 数码爱好者

管理手机、电脑、相机、耳机、NAS、路由器等数码设备。

主要诉求：

- 记录购买价格、保修期、序列号。
- 统计设备投入和维修成本。
- 保存说明书和购买凭证。

## 4. 核心业务闭环

```text
创建设备档案
  ↓
录入购买信息和保修期限
  ↓
上传发票、保修卡、说明书等附件
  ↓
配置耗材更换周期
  ↓
系统定时生成保修和耗材提醒
  ↓
设备故障时创建维修记录
  ↓
跟踪维修状态和维修费用
  ↓
维修完成后归档处理结果
  ↓
首页看板展示设备、提醒、费用和状态
  ↓
AI 辅助提取票据信息、生成排查建议和维护总结
```

## 5. 角色与权限

### 5.1 系统管理员（二期）

适用于本地部署或演示场景。当前版本暂未实现独立系统管理员和 RBAC 后台；关键家庭协作操作日志已经支持落库和分页查询，完整系统管理后台作为后续增强。

权限：

- 管理系统用户。
- 查看系统操作日志。
- 管理基础字典和系统配置。

### 5.2 家庭空间所有者

家庭空间创建者。

权限：

- 管理家庭空间信息。
- 邀请已注册用户加入家庭空间。
- 调整家庭成员角色。
- 移除家庭成员，但不能移除当前登录用户或让家庭空间失去最后一个所有者。
- 管理所有设备、保修、耗材、维修和附件。
- 查看统计看板。

### 5.3 家庭成员

被邀请加入家庭空间的用户。当前版本已支持由家庭所有者邀请已注册用户、调整角色和移除成员。

权限：

- 查看家庭空间内设备。
- 新增或编辑维修记录。
- 新增耗材更换记录。
- 查看附件。

### 5.4 只读成员（二期）

权限：

- 只能查看设备、保修、耗材、维修和附件。
- 不能新增、编辑、删除数据。

## 7. 不做什么

第一版明确不做：

- 不做商城购物流程。
- 不做企业固定资产盘点。
- 不做复杂审批流。
- 不做财务报销系统。
- 不做品牌设备远程控制。
- 不做智能家居协议接入。
- 不做强医疗、法律、保险建议。
- 不依赖 AI 完成核心业务。

## 8. 功能需求明细

### 8.1 用户认证

用户可以注册账号并登录系统。

需求：

- 支持用户名或邮箱登录。
- 密码加密存储。
- 登录成功返回 Access Token。
- 支持退出登录。
- 后端接口默认需要认证，登录注册接口除外。

验收标准：

- 未登录访问受保护接口会被拒绝。
- 登录后可以访问家庭空间和设备接口。
- 密码不能明文存储。

### 8.2 家庭空间

用户登录后至少拥有一个家庭空间。

需求：

- 创建家庭空间。
- 修改家庭空间名称。
- 查询用户所属家庭空间列表。
- 切换当前家庭空间。
- 刷新页面或切换账号后，前端恢复的当前家庭必须属于当前用户可访问家庭列表；若本地缓存失效，应自动切到可访问家庭或清空家庭上下文。
- 邀请已注册家庭成员。
- 调整家庭成员角色。
- 移除家庭成员。

验收标准：

- 设备、保修、耗材、维修数据必须归属于家庭空间。
- 用户不能访问不属于自己的家庭空间数据。
- 家庭所有者可以邀请已注册用户加入家庭、调整角色和移除成员。
- 成员协作操作不能让家庭空间失去最后一个所有者。

### 8.3 设备分类

用于按设备类型组织设备。

需求：

- 新增分类。
- 编辑分类。
- 删除分类。
- 分类排序。
- 系统内置常用分类；注册默认家庭和手动创建家庭时自动初始化默认分类。

默认分类建议：

- 数码设备。
- 大家电。
- 小家电。
- 网络设备。
- 厨房设备。
- 清洁设备。
- 家居设备。
- 其他。

验收标准：

- 设备可以绑定分类。
- 删除分类前需要判断是否存在设备。
- 新建设备时，前端可以基于家庭默认分类预选兜底分类，但用户仍可手动调整。

### 8.4 设备档案

设备档案是系统核心对象。

字段建议：

- 设备名称。
- 品牌。
- 型号。
- 序列号。
- 分类。
- 所属家庭空间。
- 购买日期。
- 购买渠道。
- 购买价格。
- 存放位置。
- 当前状态。
- 备注。

状态：

- 正常使用。
- 待维修。
- 维修中。
- 已维修。
- 闲置。
- 已报废。

验收标准：

- 可以分页查询设备列表。
- 可以按分类、状态、品牌和关键字筛选；保修状态展示/筛选作为后续增强。
- 设备详情页能看到保修、耗材、维修和附件信息。

### 8.5 保修管理

记录设备保修期限和保修凭证。

需求：

- 创建设备保修记录。
- 编辑保修开始日期、结束日期、保修类型。
- 记录售后电话、售后地址、售后说明。
- 设置提前提醒天数。
- 自动识别即将过保设备。

验收标准：

- 保修结束日期不得早于保修开始日期。
- 首页展示即将过保设备数量。
- 同一设备同一天不重复生成过保提醒。

### 8.6 附件管理

用于保存发票、保修卡、说明书、维修单和售后截图。

需求：

- 上传附件。
- 绑定附件到设备、保修记录或维修记录。
- 查询设备附件列表。
- 下载附件。
- 删除附件。

支持类型：

- JPG / JPEG / PNG。
- PDF。
- WebP、DOC / DOCX 作为二期扩展。

验收标准：

- 文件上传需要校验大小和类型。
- 非家庭空间成员不能访问附件。
- 附件元数据入库。

### 8.7 耗材管理

用于管理需要周期更换的耗材。

示例：

- 净水器滤芯。
- 空气净化器滤网。
- 扫地机器人边刷。
- 电动牙刷刷头。
- 门锁电池。
- 遥控器电池。

需求：

- 新增耗材项。
- 设置更换周期。
- 设置上次更换日期。
- 自动计算下次更换日期。
- 记录每次更换。
- 支持提前提醒。

验收标准：

- 更换耗材后自动刷新下次提醒日期。
- 首页展示即将到期和已逾期耗材。

### 8.8 维修记录

用于记录设备故障和维修过程。

需求：

- 创建维修记录。
- 填写故障描述。
- 记录故障发生时间。
- 记录维修渠道。
- 记录维修费用。
- 上传维修单或售后截图。
- 状态流转。
- 完成维修后填写处理结果。

状态流转：

```text
待处理 -> 已报修 -> 维修中 -> 已完成
       └──────────────-> 已取消
```

验收标准：

- 状态只能按规则流转。
- 维修完成后可以同步更新设备状态。
- 已取消维修不计入维修费用统计。

### 8.9 提醒任务

提醒任务由系统定时扫描生成。

提醒类型：

- 保修即将到期。
- 保修已到期。
- 耗材即将更换。
- 耗材已逾期。
- 维修待跟进（当前仅作为类型预留，定时扫描暂未生成）。

当前实现说明：

- 已由定时任务生成保修即将到期、保修已到期、耗材即将更换和耗材已逾期提醒。
- 维修待跟进保留枚举和文档位置，后续在维修流程深化时再接入扫描规则。

需求：

- 定时扫描需要提醒的事项。
- 生成提醒任务。
- 生成站内通知。
- 外部渠道启用时，在同一事务中写入待投递记录，但不调用外部服务。
- Redis 去重。
- 支持用户标记已读。

验收标准：

- 同一业务对象同一天同一提醒类型不重复提醒。
- 提醒生成失败不会影响设备、保修、耗材数据。
- 邮件或 Webhook 失败只更新通知记录并按配置重试，不回滚提醒和站内通知。
- 达到最大尝试次数后停止自动重试，保留失败原因用于排障。

### 8.10 我的家首页 / 看板

当前前端已将首页产品表达升级为“我的家”，路由仍使用 `/dashboard`，用于快速了解家庭设备状态。

展示内容：

- 设备总数。
- 即将过保设备数量。
- 已过保设备数量。
- 即将更换耗材数量。
- 已逾期耗材数量。
- 维修中设备数量。
- 本月维修费用。
- 设备分类分布。
- 最近提醒。
- 最近维修记录。

验收标准：

- 统计数据按当前家庭空间隔离。
- 首页接口已使用 Redis 缓存完整摘要；缓存未命中、值非法或 Redis 不可用时回源单次数据库聚合查询。

### 8.11 AI 辅助

AI 只作为辅助能力。

场景：

- 发票文本提取设备信息。
- 故障描述生成排查建议。
- 维修历史生成维护总结。
- 耗材更换记录生成保养建议。

约束：

- 必须支持关闭 AI。
- 必须支持 Mock 模式。
- AI 失败不影响核心业务。
- AI 结果不能自动覆盖用户数据，必须由用户确认。

验收标准：

- 未配置真实 API Key 时系统可正常启动。
- AI 接口失败时返回明确提示，不影响保存维修记录。

### 8.12 PWA 安装与离线外壳

PWA 用于让家庭成员把 FixLedger 安装到手机或桌面，并以独立窗口启动。它是现有响应式 Web
应用的增强，不另起一套客户端，也不改变后端鉴权边界。

需求：

- 提供应用名称、图标、主题色、启动地址和独立窗口显示模式。
- 浏览器确认满足安装条件时，提供明确的“安装到设备”操作。
- 网络断开时展示可识别的离线状态和重试入口。
- 新版本准备完成后由用户确认刷新，不在用户填写表单时强制更新。

安全边界：

- Service Worker 不缓存 `/api`、附件下载、Actuator、Swagger 或任何带鉴权语义的响应。
- 不缓存 JWT、家庭信息、设备、保修、耗材、维修、提醒和 AI 结果。
- 第一版不支持离线新增、编辑、删除和后台同步，避免产生数据冲突。
- PWA 安装和 Service Worker 依赖安全上下文；生产和手机局域网安装必须使用 HTTPS，只有同设备 `localhost` 可在 HTTP 下调试。

验收标准：

- 支持 PWA 的浏览器可以识别应用清单并安装 FixLedger。
- 已安装应用从 `/dashboard` 启动，未登录时仍由现有路由守卫跳转登录页。
- 离线访问导航请求时返回本地离线页，恢复网络后可以重新进入应用。
- PWA 更新、安装和网络状态变化不会影响现有登录与业务接口行为。

## 9. 非功能需求

### 9.1 安全性

- 密码必须加密存储。
- JWT 密钥不能提交到代码仓库。
- 附件访问必须鉴权。
- 日志中不能输出密码、Token、API Key。
- AI 调用不能发送敏感信息。

### 9.2 性能

- 常见列表接口必须分页。
- 首页摘要使用短 TTL Redis 结果缓存，Redis 失败时必须回源数据库。
- 设备、保修、耗材和维修写操作成功提交后必须失效对应家庭的首页摘要缓存。
- 首页摘要的数据库回源必须使用单次聚合查询，避免固定执行多次统计查询。
- 同步 CSV 导出默认不得超过 5000 行，超过阈值时明确拒绝而不是静默截断。
- 附件上传限制大小。
- 定时任务批量处理。

### 9.2.1 可观测性

- 使用 Micrometer 记录 HTTP 请求、首页缓存命中结果、首页回源耗时和导出结果。
- Actuator 默认只公开健康和基础信息；指标端点必须显式配置，并放在受控网络边界后。
- 日志不得输出缓存正文、导出内容、Token、密码或家庭业务明细。
- 慢查询排查必须基于指标、执行计划和索引，不通过生产环境开启全量 SQL DEBUG 日志实现。

### 9.3 可维护性

- 后端按模块分包。
- 统一异常处理。
- 统一响应结构。
- 统一 Redis Key 管理。
- 接口文档与代码同步。

## 10. 验收标准

MVP 完成时应满足：

- 可以通过 Docker 启动后端、前端、MySQL、Redis 和 RustFS。
- 用户可以注册登录。
- 用户可以创建家庭空间。
- 用户可以管理设备档案。
- 用户可以上传设备附件。
- 用户可以管理保修记录。
- 用户可以管理耗材和更换记录。
- 用户可以创建和处理维修记录。
- 系统可以生成保修和耗材提醒。
- 我的家首页可以展示核心统计、本周事项和家庭日历。
- 用户可以导出家庭设备资产清单和维修费用报表 CSV。
- 新家庭空间没有设备时，前端应提供明确的“创建第一台设备”入口。
- 空设备引导必须等待真实数据加载完成后再展示；设备搜索无结果应与家庭无设备区分。
- AI Mock 模式可用。
- README、接口文档、数据库文档齐全。
- `docs/spec.md` 和 `docs/decisions/` 能说明项目边界、成功标准和关键架构取舍。

## 11. P10.1 当前需求实现对齐说明

截至 P10.1 需求复核，当前实现已经覆盖 MVP 核心闭环：注册登录、家庭空间、设备分类、设备档案、保修记录、RustFS/本地附件、耗材周期、维修记录、提醒任务、站内通知、我的家首页、Mock AI 和 Docker 一键启动。

当前已实现但需要继续打磨的能力：

- 家庭空间已有成员关系和权限校验，家庭所有者可邀请已注册用户、调整角色和移除成员。
- 设备分类支持增删改查，新家庭空间会自动初始化默认分类。
- 前端会在登录态恢复和家庭列表刷新后校正当前家庭上下文，避免使用本地缓存中的失效家庭 ID 访问业务接口。
- 总览和凭证盒已提供新用户首设备引导，并收口加载态和搜索无结果的区分。
- 设备列表当前支持关键字、分类、状态和品牌筛选，保修状态字段在列表响应中保留扩展位但不作为当前筛选条件。
- 首页刷新标记已替换为短 TTL 统计结果缓存，并在业务写事务提交后按家庭主动失效。
- 文件存储当前优先接入 RustFS 对象存储，本地文件系统保留为测试和兜底；MinIO 或其他 S3 兼容服务可复用同一实现。
- AI 当前支持 Mock 和 OpenAI-compatible Client 基础实现，默认关闭真实 Provider。
- 提醒已支持保修和耗材扫描、Redis 去重、站内通知以及可选邮件/Webhook Outbox 投递；维修待跟进仍为后续增强。
- 系统管理员、RBAC 和系统字典页面暂未实现；关键家庭协作操作日志已进入当前实现。
- 家庭数据导出已进入当前实现：设备资产清单和维修费用报表以同步 CSV 下载方式提供，导出接口仍校验家庭成员权限，并对 CSV 转义和公式注入风险做基础防护。
- 移动响应式与 PWA 已进入当前实现：手机端采用独立信息架构，支持安装、离线状态页和用户可控更新；Service Worker 不缓存业务接口与鉴权响应。
- 当前规格文档已补充到 `docs/spec.md`，关键决策已补充到 `docs/decisions/`，后续需求变化要先更新文档再实现。
